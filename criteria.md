# Acceptance criteria — FitFindr

Five criteria that say what "working" means for this agent, written in unit 3
**before** any results existed.

An acceptance criterion names a target: a number, a count, a rate, or something
a person could plainly observe. *"The agent handles errors"* is an opinion.
*"When search returns nothing, the agent stops before calling the second tool,
in 5 of 5 tries"* is a criterion.

Under each one, write a sentence or two on **why that target** and not a
stricter one. A reason that says something about your tools, your loop, or the
data earns credit; *"80% seemed reasonable"* does not.

> Missing your own targets next unit costs you nothing. Setting a target so
> easy you can't miss it does.

**Two are written for you. You write three.**

---

## 1. A matching query completes all three tools

Given a query that matches at least one listing, the agent completes all three
tool calls and returns a fit card — in at least 4 of 5 tries.

**Why this target:**
Because the agent's search step relies on relatively simple keyword matching. Some valid queries may use wording that doesn't oeverlap weill with the listing text, causing an occasional search miss even when a relevant listing exists. 4/5 successful tests make workflow is reliably reproducible.

---

## 2. An impossible query stops before the second tool

Given a query that matches no listings, the agent stops before calling
`suggest_outfit` and returns a message naming what to change — 5 of 5 tries.

**Why this target:**
We require 5/5 here because the no-match case has a more clearly stopping condition, once search returns no listings, the agent should avoid calling suggest_outfit and explain what the user can change. This path has less search and interpretation than the successful-match path.

---

## 3. Something about state
We need to verify that the item selected by one tool is the same item that is actually passed to the next tool. Instead of only saving a key-value pair such as the user ID in a JSON file, the state should also record the source of that value, such as the tool call ID and the file or field path where it came from.

Each tool should receive explicit arguments, and we should compare those arguments with the value stored in the session state. For example, after a search tool selects an item, we could store it in session["selected_item"] together with its source metadata. Before or when suggest_outfit is called, we can compare the item in session["selected_item"] with the actual item argument received by suggest_outfit.

A countable metric would be the number or percentage of tool calls in which the selected item in the session exactly matches the item received by the next tool.

Why this target:
State failures are difficult to detect because they often appear to be tool failures. By explicitly comparing the stored state with the arguments that actually reach the next tool, we can directly measure whether information is being preserved correctly across tool calls.

## 5. Your choice

I would check whether the search tool respects the user's price ceiling.

| Check | Evidence | Pass condition |
|---|---|---|
| Price ceiling | Compare the price of every returned item with the maximum price specified by the user | Required: 100% of returned items must have a price less than or equal to the user's maximum price |

**Why this target:**  
Price is a hard constraint rather than a stylistic preference. If a user sets a maximum price, recommending an item above that limit makes the search result unusable even if the item otherwise matches the request. This target is also easy to measure by comparing each returned item's price with the user's specified price ceiling.
